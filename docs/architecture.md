# Архитектура

Glass — это не «обёртка над чужим интерпретатором», а полный конвейер: от текста программы до выполнения на собственной стековой VM с собственным сборщиком мусора. Всё написано на C++17 и находится в каталоге `src`.

## Конвейер

```
исходный текст
   │  lexer     лексер: токены; автоматическая вставка `;` в конце строки
   ▼
   │  parser    парсер всей грамматики → дерево (AST)
   ▼
   │  sema      декларации: наследование, контракты facet, правила virtual/override
   ▼
   │  BodyChecker   типы внутри тел функций; статические ошибки
   ▼
   │  codegen   компилятор в байткод + описание классов (vtable, раскладка полей)
   ▼
   │  vm        стековая VM: выполнение, виртуальные вызовы, исключения, сборщик мусора
```

| Каталог | Содержимое |
|---|---|
| `src/lexer` | `Lexer` и токены; правило автоматической вставки `;` (в том числе «не вставлять перед `else`/`catch`/`finally`») |
| `src/parser`, `src/ast` | рекурсивный спуск по [грамматике](../glass-grammar.md); узлы выражений, операторов и деклараций |
| `src/sema` | `Sema` (проверка деклараций) и `BodyChecker` (типы тел функций) |
| `src/codegen` | `Compiler`: AST → байткод и `ClassInfo` |
| `src/bytecode` | опкоды (`Chunk.h`), значения (`Value`), объекты кучи (`Obj.h`), встроенные функции (`Builtins.h`), описание класса (`ClassInfo.h`) |
| `src/vm` | `VM`: цикл выполнения, отладочные шаги, исключения, сборщик мусора, интроспекция |
| `src/prelude` | библиотека, написанная на самом Glass: `Exception` и служебные типы интроспекции |
| `src/capi` | C API ([описание](c-api.md)) |
| `src/repl` | интерактивная консоль |

## Значения и объекты

Значение (`Value`) — это `std::variant` из пяти видов: целое (64 бита), `double`, `bool`, «пусто» (`null`), строка (разделяемая неизменяемая) и две ссылки — на объект (`ObjInstance`) и на массив (`ObjArray`). Объект кучи хранит ссылку на описание своего класса и плоский набор «слотов» полей по 8 байт — поэтому в `~layout` смещения идут слотами, а размер каждого поля — 8 байт.

## Байткод и VM

Байткод — это стековая машина: операнды кладутся на стек, инструкции берут их оттуда. Каждый вызов функции — отдельный фрейм со своим местом на стеке для локальных переменных. Набор опкодов (арифметика, переходы, вызовы, работа с полями и массивами, исключения, интроспекция, печать) описан в [`src/bytecode/Chunk.h`](../src/bytecode/Chunk.h).

**Виртуальный вызов.** У класса есть таблица `vtable`: *имя метода → функция*. `CallVirtual` берёт объект-получатель, смотрит в таблицу его реального класса и вызывает найденную реализацию — поэтому вызов зависит от класса объекта, а не от типа переменной. В таблицу попадают только виртуальные методы (`virtual`/`override`, реализации `facet`, `toString()`); обычные методы вызываются напрямую. Поиск идёт по имени, а не по номеру слота — сознательное упрощение (см. [README](../README.md), «Сознательные упрощения»).

**Проверки во время выполнения.** Приведение `(Dog) animal` проверяет реальный класс объекта (опкод `CheckCast`); `print` и `+` вызывают `toString()` (опкод `ObjToString`) — оба действуют как обычный вызов, поэтому отладчик может войти в `toString` шагом.

**Исключения.** `throw` разматывает фрейм за фреймом в поисках подходящего `catch`: подходит исключение того же класса, его потомка или реализующее нужный `facet`. Ошибки самой VM (деление на ноль, выход за границы, неверное приведение) — не исключения Glass: они останавливают программу с сообщением.

**Отладка.** Точки останова — по номерам строк; шаги с заходом, обходом и выходом вычисляются по смене строки и глубине стека вызовов. Эту же возможность через C API использует IDE.

## Сборщик мусора

Сборка — mark-and-sweep. Все объекты кучи связаны в список, у каждого есть пометка `marked`.

1. **Mark.** Корни — весь стек VM, включая временные значения посреди вычисления выражения. Обход помечает всё, до чего можно добраться по ссылкам (циклические ссылки не мешают).
2. **Sweep.** Список объектов просматривается; непомеченные освобождаются, пометки сбрасываются.

Сборка запускается автоматически, когда число живых объектов достигает порога (сначала 64, после каждой сборки — «живых × 2 + 32»), и по требованию: оператор `~gc`, функция `glass_collect_garbage`, кнопка «Собрать мусор» в IDE. Снимок кучи (`~heap`, `glass_get_heap_json`) помечает у каждого объекта, достижим ли он, — на схеме кучи недостижимые показаны как «мусор» до ближайшей сборки.

## Слои среды разработки

```
glass_capi (C++)           C API поверх VM
   ▲
Glass.Interop (.NET)       P/Invoke, GlassSession
   ▲
Glass.Studio.Core (.NET)   view-model'и, курс, журнал, карточки — без WPF, тестируется на любой ОС
   ▲
Glass.Studio (WPF)         тонкие окна: XAML и немного кода «склейки»
```

Благодаря такому разделению почти вся логика IDE проверяется обычными тестами на настоящей VM, а XAML — линтером, который сверяет привязки с типами ядра без Windows.
