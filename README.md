# Glass — компилятор, VM и IDE «Glass Studio»

[![CI](https://github.com/sxansee/glass-lang/actions/workflows/ci.yml/badge.svg)](https://github.com/sxansee/glass-lang/actions/workflows/ci.yml)
[![License: MIT](https://img.shields.io/badge/license-MIT-blue.svg)](LICENSE)
[![Release](https://img.shields.io/github/v/release/sxansee/glass-lang?include_prereleases)](https://github.com/sxansee/glass-lang/releases)

> **English.** Glass is a statically typed object-oriented teaching language that makes the runtime visible. Most languages hide how an object is laid out in memory, how a virtual call is dispatched and how the garbage collector works; Glass ships built-in introspection operators (`~layout`, `~vtable`, `~address`, `~heap`, `~gc`) that show exactly that. The repository contains the whole toolchain — lexer, parser, semantic analyzer, bytecode compiler, a stack VM with a mark-and-sweep GC, a C API — and **Glass Studio**, a WPF IDE with a step debugger and a heap visualizer. It targets 2nd–3rd year students studying OOP and compilers. The language documentation is in Russian. To build and test: `bash scripts/test-all.sh` (Linux/macOS) or `.\scripts\test-all.ps1` (Windows); see [CONTRIBUTING.md](CONTRIBUTING.md). MIT licensed.

Полный компилятор и VM для языка Glass: лексер, парсер, семантический
анализатор, байткод-компилятор, стековая VM с mark-and-sweep GC — весь язык
из `glass-grammar.md` (объекты, массивы, исключения, интроспекция), плюс
интерактивная консоль (REPL), C API и **Glass Studio** — WPF-среда с редактором,
пошаговым отладчиком, схемой кучи и инспектором объекта (каталог `dotnet/`,
см. `dotnet/README.md`). Формальная грамматика — рядом, в `glass-grammar.md`.

## REPL (интерактивная консоль)

Запуск без аргументов — способ опробовать уже готовую часть языка, не заводя
`.glass`-файл на каждую мелочь. Движок не умеет дописывать код в уже
запущенную VM, поэтому у REPL главное упрощение: каждый фрагмент заново
компилирует и исполняет **всю сессию целиком**, но на экран печатается
только то, что не показывалось на предыдущих шагах — накопление не выглядит
как повторяющийся спам в консоли.

- `mold`/`facet`/`fn` (кроме `main`) копятся как декларации сессии; любой
  другой оператор — очередная строка тела синтетического `main`. Можно
  вставлять многострочные `mold`/`fn` целиком — фрагмент исполняется, как
  только фигурные скобки сбалансированы.
- Ошибка на любой фазе (разбор/семантика/типы/байткод/выполнение) не ломает
  сессию — фрагмент откатывается, состояние остаётся как было до него.
- Мета-команды: `:show` — текущая собранная программа, `:reset` — очистить
  сессию, `:cancel` — прервать незакрытый многострочный ввод, `:help`,
  `:quit` / `:exit` / Ctrl+D.
- `fn main()`, введённая вручную, не сливается с сессией — разовый запуск
  деклараций сессии с этой main вместо синтетической, без побочных эффектов
  на statements/declarations.

Реализация — `src/repl/`, отдельная библиотека `glass_repl`, не трогает
lexer/parser/sema/codegen/vm и не покрыта существующими 384 C++-проверками (они
проверяют библиотеки напрямую, не сам `glassc`).

## Сборка в Visual Studio 2022+

Открыть папку `glass/` через **Файл → Открыть → Папку** — Visual Studio сама распознает `CMakeLists.txt` и сконфигурирует проект (CMake Tools встроены). Цели `glassc`, `glass_capi` и все одиннадцать `*_tests` появятся в выпадающем списке «Выбор элемента запуска». Запускать (F5) можно `glassc.exe` и `*_tests.exe`; **`glass_capi.dll` — библиотека, её только собирают** (**Сборка → Собрать всё**). Если выбрать её элементом запуска, Visual Studio ответит «Отсутствует исполняемый файл цели» — это не ошибка сборки.

Для Glass Studio (WPF): **Сборка → Собрать всё** (получится `out\build\x64-Debug\glass_capi.dll`), затем **Файл → Открыть → Проект или решение** → `dotnet\Glass.slnx`, назначить запускаемым проект `Glass.Studio` и F5 — он сам скопирует DLL из `build\<Config>` или `out\build\x64-<Config>` (конфигурации должны совпадать: Debug ↔ x64-Debug, Release ↔ x64-Release). Подробности и список того, что проверено и что нет, — `dotnet/README.md`.

## Сознательные упрощения (важно помнить)

- **vtable — по имени метода, а не по фиксированному слоту.** Facet может реализовываться molds с разным набором и порядком виртуальных методов — единой на всех позиционной нумерации слотов без отдельной таблицы на facet (itable) не получить. Строковый поиск в `std::unordered_map<std::string, int>` — простое и корректное решение для этой фазы; медленнее позиционного слота, но не является узким местом для учебного языка. `super.method(...)` — всегда статическая диспетчеризация в обход vtable, как и полагается.
- **Стандартной библиотеки почти нет.** `Exception` — уже настоящий mold (см. `prelude/Prelude.h`: подмешивается в AST до Sema, дальше живёт как любой другой mold — наследование, vtable, GC, всё как у пользовательских типов, без спецкейсов). `List<T>`, `Canvas` — по-прежнему нигде не объявлены; BodyChecker считает такие типы «непрозрачными» и не проверяет операции над ними (см. комментарий в `BodyChecker.h`). `print` — единственная встроенная функция; конкатенация `+` для строк определена только `string + string`, не `string + int`.
- **Дженерики без подстановки**: `T` внутри `mold Box<T>` совместим с чем угодно.
- **Локальные переменные — плоское распределение слотов** без переиспользования (каждый `let`, включая объявленные внутри `if`/`while`/`try`, получает свой слот на весь вызов функции) — простое и корректное решение, чуть расточительное по стеку.
- **`return`/`break`/`continue` внутри try/catch, защищённого `finally`, не поддерживаются** — компилятор честно отказывает (codegen-ошибка), а не молча пропускает finally. `finally` компилируется дважды — на пути «поймано/не бросало» и на пути «не поймано здесь, но обязан выполниться перед тем, как исключение пойдёт дальше» (см. `Compiler::visit(TryStmt&)`) — довести это до каждой точки раннего выхода не входило в объём этой фазы. Без `finally` — return/break/continue из try/catch работают как обычно.
- **Неявный корневой тип `Glass`, о котором говорит раздел 3 grammar.md** («каждый объект по умолчанию прозрачен для интроспекции»), не заведён механически в Sema как настоящий базовый mold для всех остальных — это потребовало бы трогать разрешение цепочки наследования (`getMoldChain` и всё, что на него полагается), а не добавлять новое поверх готового, как везде до этого в проекте. Эффект — тот же: `~layout`/`~vtable`/`~address` работают на ЛЮБОМ mold-объекте без исключения, потому что читают его `ClassInfo` напрямую, а не проверяют, есть ли `Glass` среди предков.
- **`~layout`/`~vtable`/`~heap` возвращают настоящие объекты** (`LayoutInfo`/`VTableInfo`/`HeapSnapshot` — те же prelude-molds, что и `Exception`), а не голую строку — их поля (`fieldNames`, `methodNames`, `addresses` и т.д.) можно читать из Glass-кода как угодно. Дополнительно для этих трёх типов `print()` показывает готовую читаемую строку вместо `Класс@0x…` (см. `Value.cpp: describeIntrospectionObject`) — исключение сделано намеренно: интроспекция должна быть видна сразу, без ручного обхода полей, а `Класс@0x…` для инструмента, чей смысл — «покажи мне, что внутри», было бы ироничным.

## Что умеет и чего не умеет текущая VM

Работает — весь язык этой фазы, целиком: функции, рекурсия, арифметика, `if`/`while`/`for x in a..b`, `break`/`continue`, `print`; **объекты** — конструкция mold'ов (без `new`), поля (чтение/запись, включая унаследованные), методы (виртуальные — через facet или `override`/`virtual` — и статические), `this`/`super` (включая цепочку конструкторов), вызов методов своего объекта без `this.`, модификаторы доступа `public`/`private`/`protected` (проверяются при компиляции); **массивы** — `[Type]` как объекты в той же куче под тем же GC, литералы (`[a, b, c]`, `[]` с контекстом типа), индексация на чтение/запись (включая составное присваивание `arr[i] += x`), `for x in массив`, произвольная вложенность; **исключения** — `throw`, `try`/`catch` (несколько catch подряд, тип сопоставляется по цепочке mold-наследования и facet'ам — базовый `catch e: Exception` ловит и потомков), `finally` (на путях «нормально», «поймано», «не поймано этим try»), исключение из вызванной функции корректно разворачивает фреймы до подходящего catch у вызывающего; **интроспекция** — `~address` (адрес как int), `~layout` (свои и унаследованные поля объекта, плоско, со смещениями и условными размерами), `~vtable` (какая реализация метода реально вызовется — override корректно показывает класс-переопределитель, а не базовый), `~heap` (снимок всей кучи целиком), `~gc` (сборка мусора по требованию, не дожидаясь порога). Автоматический mark-and-sweep GC с растущим порогом срабатывания трассирует все эти случаи корректно — объект, живой только через массив; пойманный и более не нужный `Exception`; сами объекты интроспекции, если их никуда не сохранили — не собирая раньше времени и не удерживая лишнего.

Не работает — упирается в понятную ошибку компиляции (или, для return/break/continue сквозь `finally`, отдельно описанное ограничение выше), а не падает исподтишка: то, что явно вне рамок этой фазы — `List<T>`, `Canvas`, генерики с реальной подстановкой типов, полноценная стандартная библиотека.

**Пойманный по пути баг, стоящий отдельного упоминания (см. историю правок `VM.cpp`):** `NewInstance` изначально запускал проверку на GC *внутри* аллокации, до того как указатель на новый объект попадал на стек. GC успевал отработать mark-фазу (свежий объект ещё нигде не виден как корень) и sweep — удаляя объект прямо во время его создания, до первого использования. Классическая ошибка "preliminary collection". Починено: GC теперь проверяется строго после `push()` нового объекта, когда он уже сам себе корень. `OpCode::NewArray`, `allocateArray` и — три фазы спустя — `OpCode::Layout`/`Vtable`/`Heap` сразу писались с учётом этого — тот же порядок обязанностей, без повторения ошибки.

## C API (`src/capi/`)

`GlassApi.h`/`.cpp` — `extern "C"`-обёртка вокруг готовой VM для встраивания
в другой процесс, в первую очередь в WPF через P/Invoke (см. `dotnet/`).
Собирается как отдельная SHARED-цель `glass_capi` (`.so` здесь, `.dll` на
Windows — исходник один, `GLASS_API` в заголовке сама разруливает разницу
между `dllexport` и `visibility("default")`).

- **Жизненный цикл**: `glass_compile(source, &error)` — тот же пайплайн,
  что в `glassc` (включая prelude), возвращает handle сессии или `NULL` с
  диагностикой; `glass_session_free`, `glass_free_string`.
- **Запуск**: `glass_run`, `glass_get_output`, `glass_has_error`/`glass_get_error`.
- **Отладка**: `glass_set_breakpoint`/`clear`, `glass_run_until_pause`,
  `glass_step_into`/`over`/`out`, `glass_current_line` — тонкие обёртки
  над готовым `VM::stepInto()` и др. Отладчик работает в режиме «Just My
  Code»: строки пролога (`Exception` и др.) отрицательные, поэтому точки
  останова и шаги никогда не попадают в служебный код.
- **Для IDE**: `glass_request_stop` — ЕДИНСТВЕННЫЙ вызов, допустимый из другого
  потока, пока основной внутри `glass_run`/`glass_step_*` (атомарный флаг; VM
  проверяет его перед каждой инструкцией и завершается как при рантайм-ошибке
  «выполнение прервано») — без него зависшую программу студента (`while true {}`)
  пришлось бы убивать вместе с IDE. `glass_collect_garbage` — немедленный `~gc`
  между шагами (возвращает число освобождённых объектов).
  `glass_get_object_info_json` — раскладка полей и vtable одного объекта: тем
  же кодом (`VM::layoutOf`/`vtableOf`), что считает `~layout`/`~vtable` в самом
  языке, — инспектор не может разойтись с тем, что напечатает программа.
- **Инспекция в JSON**: `glass_get_call_stack_json`, `glass_get_locals_json`,
  `glass_get_heap_json` — через границу C нет естественного способа вернуть
  список записей переменной длины без ручного маршалинга структур, JSON
  простой и одинаково проверяется тестами. Объекты/массивы в locals —
  только ссылка по адресу (`{"ref": "...", "kind": "object", ...}`), сами
  данные — в heap-снимке под тем же адресом: так получается граф для
  визуализации (узлы — объекты, рёбра — ссылки), а не неограниченное
  разворачивание вглубь, которое циклами в куче не сломать. Каждый
  объект снимка помечен `reachable` — достижим ли он от корней GC (весь
  стек VM, включая временные значения): `false` — ровно то, что освободит
  следующая сборка мусора. `double` в JSON всегда с точкой или экспонентой
  (`3.0`, не `3` — иначе тип не отличить от `int`); `inf`/`nan` (не JSON-числа)
  приходят как `{"kind": "double", "text": "inf"}`.
- **Владение памятью** — одно правило на все функции, возвращающие `char*`:
  всегда свежевыделенная строка, освобождать только через `glass_free_string`.
  Аллокатор и освобождение — в одном модуле намеренно (на Windows смешение
  аллокаторов между DLL и хостом — известный источник "работает в debug,
  падает в release").

Тестируется `tests/capi_tests.cpp` — те же функции с C-линковкой вызываются
напрямую из C++ (это и есть настоящая проверка границы: те же символы, то
же соглашение о вызове, что увидит P/Invoke). Все 21 экспорт — ровно то,
что объявлено в заголовке (проверено `nm -D`).

**Про `-fPIC`:** чтобы встроить статические библиотеки проекта в `.so`,
они обязаны быть собраны как position-independent — выставлено один раз
глобально (`CMAKE_POSITION_INDEPENDENT_CODE`), а не на каждой цели.

## Возможности языка, добавленные в этой версии

Найдено при реальном использовании (print не печатал строку с числом, `for` по `range` не работал, срезов не было, касты ничего не делали) и исправлено — каждый пункт покрыт тестами (`tests/language_tests.cpp`):

- **`print(a, b, c)`** — любое число значений любых типов через пробел; `print()` — пустая строка. Массивы печатаются как `[1, 2, 3]` (строки внутри — в кавычках).
- **Строки.** `"x = " + 5` (число/bool/массив рядом со строкой превращается в текст), `"ab" * 3`, сравнение `<`/`>` по алфавиту, `s[i]`, `s[-1]`, срезы, `for c in "текст"`. Длина, индексы и срезы считаются в **символах** (кириллица работает), `upper()`/`lower()` понимают кириллицу.
- **Преобразования типов.** `int(x)`, `double(x)`, `bool(x)`, `str(x)` и приведения `(int) 3.7`, `(string) 5`. Раньше `(int) 3.7` молча ничего не делало. Неявное `int → double` теперь реально превращает значение: `let d: double = 5; print(d / 2)` — `2.5` (раньше было `2`).
- **`else`, `catch`, `finally` с новой строки.** Стиль `}` ⏎ `else {` теперь разбирается: лексер не вставляет `;` после `}`, если следующее слово — `else`, `catch` или `finally`.
- **`print(объект)` и `toString()`.** Без `toString` объект печатается как `Класс@0x…` (hex, тот же адрес, что у `~address`; раньше было `<object @…>`). Метод `fn toString() -> string` без параметров неявно виртуален и вызывается по реальному классу объекта в `print`, `"текст" + объект`, `s += объект`, `str(объект)` и `(string) объект` (новый опкод `ObjToString`; в отладчике в `toString` можно зайти шагом). Элементы массива печатаются без `toString`.
- **Приведение ссылочных типов проверяется во время выполнения.** `(Dog) animal` смотрит на реальный класс объекта (новый опкод `CheckCast`): `null` проходит, чужой класс — ошибка выполнения «нельзя привести объект класса 'Cat' к 'Dog'». Заведомо невозможное (`(Cat) dog` для несвязанных mold'ов, `(Dog) 5`) отсекается ещё на этапе типов.
- **Строже правила `virtual`/`override`.** `override` допустим только над виртуальным методом базы (`virtual`/`override`, реализация facet-контракта или `toString()`); метод наследника без `override` поверх виртуального — ошибка «добавьте override». Раньше обе ситуации проходили молча, и полиморфизм просто не срабатывал.
- **`range(n)`, `range(a, b)`, `range(a, b, шаг)`** в `for` (без выделения массива) и как значение; переменная цикла больше не ломает итерацию при изменении в теле.
- **Срезы и индексы как в Python:** `xs[1:3]`, `xs[:2]`, `xs[::-1]`, `xs[-1]`; границы вне диапазона обрезаются.
- **Массивы:** `.length`, `append`, `pop`, `insert`, `remove`, `contains`, `indexOf`, `reverse`, `sort`, `clear`, `join`, склейка `a + b`. **Строки:** `upper`, `lower`, `trim`, `split`, `replace`, `contains`, `startsWith`, `endsWith`, `indexOf`, `repeat`.
- **Функции:** `len`, `abs`, `min`, `max`, `sum`, `sqrt`, `pow`, `floor`, `ceil`, `round`; константы `PI`, `E`.
- **Парсер:** `;` не нужна перед `}` — `if x { break }` на одной строке работает. **`double` печатается всегда с точкой** (`3.0`).
- Исправлено: `xs.length` роняло компилятор (внутренняя ошибка).

## Баги, пойманные по пути к IDE

При подготовке отладчика к реальной нагрузке нашлись и починены (каждый — тестом, который
до правки падал):

- **Бесконечная рекурсия роняла процесс** (`std::bad_alloc`, рост стека без предела) — для IDE это
  падение всей среды из-за одной программы студента. Теперь глубина вызовов ограничена
  (10 000) и превышение — обычная рантайм-ошибка «переполнение стека вызовов».
- **Обход при сборке мусора был рекурсивным** — на связном списке в сотни тысяч звеньев он
  переполнял стек C++. Теперь итеративный (явный рабочий список).
- **Строки пролога совпадали со строками пользователя** — точка останова на строке 5 срабатывала
  «внутри» служебного конструктора `Exception` (на его собственной строке 5), а шаг с заходом
  показывал в редакторе чужую строку. Теперь строки пролога отрицательные, отладчик
  в них не останавливается.
- **JSON-снимок терял тип `double`** (целое `3.0` писалось как `3`) и мог содержать `inf`/`nan` —
  невалидный JSON, на котором падает любой разбор. Теперь `3.0` и `{"kind":"double","text":"inf"}`.

## Курс, журнал и данные приложения

- **Курс по Glass.** В Glass Studio пункт меню **«Курс по Glass»** (рядом со «Справкой») и одноимённая кнопка на панели инструментов открывают окно курса: 24 урока в шести главах — теория, примеры и задача с автоматической проверкой. Заготовка урока загружается в редактор главного окна, «Проверить» запускает вашу программу и сравнивает вывод с ожидаемым. За урок дают до трёх звёзд (подсказка, показанное решение и лишние попытки уменьшают награду), прогресс сохраняется. Вся логика курса лежит в ядре (`Glass.Studio.Core`, `CourseViewModel`) и проверяется тестами с настоящей VM; окно (`CourseWindow`) только показывает.
- **Журнал.** Вкладка **«Журнал»** внизу слева показывает записи приложения с фильтром по уровню, кнопками «Открыть папку» и «Очистить»; в «Справке» есть пункт «Открыть папку журналов». Необработанные исключения тоже попадают в журнал.
- **Где лежат данные.** Всё в `%LOCALAPPDATA%\GlassStudio`: журналы — в подпапке `logs` (файл на день, хранятся 14 дней), прогресс курса — `course-progress.json`. Удалите папку — приложение начнёт с чистого листа.
